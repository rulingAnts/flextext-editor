# Audit: which guards belong on the server (2026-08-20)

> Seth, 2026-08-19: *"A lot of these consistency checks/drift guards probably need to live in the
> worker rather than in the client app... We've been putting those things on the client side in order
> to avoid breaking the worker or having to have a staging worker. But might be we want to rethink
> that, as long as changes are additive."* Run once the project/researcher split was proved working,
> which it was on 2026-08-20 (v433).

**Method:** enumerate every guard the client enforces, then check the worker for the same rule —
against the code, not against the plans, since three status claims in this repo were found stale the
same day. Route table generated by parsing `worker/src/v1.js` rather than by grep-and-hope.

**Headline:** there is **no case today where a client-side check is the only thing protecting another
researcher's data.** Everything that looked like one turns out to be protected by self-scoping
instead. ⚠ But self-scoping is exactly what Phase C removes, so several of these are safe for a
reason that is about to expire. That is the real finding, and it is a finding about *timing*, not
about a present hole.

---

## The principle this audit is ranked by (Seth, 2026-08-20)

> *"Gates that are client-side rather than server side are higher risk for break or collision and
> also more likely to present security vulnerabilities."*

Correct, and it is the reason F1 and F2 rank where they do. Anything enforced in `docs/js` is
enforced by code the holder of the browser can read, edit and skip. A client-side gate is a
statement about the interface, not about what the system permits.

⚠ **Two things that look like boundaries here and are not**, stated because assuming either would be
the expensive mistake:

- **CORS is advertisement, not access control.** Verified in code: `v1Cors()` chooses which
  `Access-Control-Allow-Origin` header to SET, and `originAllows()` feeds that choice — but no route
  refuses a request because of its Origin. A request carrying a valid session token is processed
  normally whatever Origin it claims; only a BROWSER declines to hand the response back to page
  script. Anything that is not a browser is unaffected. The origin list is there to stop one of our
  own pages being read by another site, which is worth having and is not a permission check.
- **The service worker is not a protected execution context.** It is inspectable (DevTools →
  Application → Service Workers → inspect gives a full console in its scope), it is fetched from our
  own origin like any other file, and nothing obliges a client to go through it at all. It is a cache
  and an offline story, never an enforcement point.

**So the boundary is exactly one thing: the checks `worker/src/v1.js` performs on an authenticated
request.** Everything else — panel gating, hidden cards, disabled buttons, the service worker, the
origin list — is user interface and defence in depth. That is the standard every finding below is
measured against, and it is why F2's ordering rule ("server filter in the same commit as the member
UI, never after") is written as non-negotiable rather than as a preference.

⚠ The corollary that is easy to lose: this is **not** an argument for moving everything server-side.
F3 is enforced client-side because the worker is structurally unable to see what it would need to
see, and F4 is client-side because it is a question about the far end's capabilities rather than the
caller's permissions. The test is not "where does this run" but **"if the client simply did not run
this check, what would happen?"** If the answer is "nothing, the worker refuses anyway", the client
check is a convenience and belongs wherever it reads best.

## F1 — `isApproved()` gates 4 of 30 researcher-authed routes, and the comment claims otherwise

`worker/src/v1.js:57` says *"isApproved() gates the privileged endpoints"*. Measured: **30 routes
call `authResearcher`; 4 call `isApproved`** (`GET /v1/researcher`, `PUT /v1/researcher/settings`,
`POST /v1/instances`, `POST /v1/researcher/drive/testfile`).

**Why it is nonetheless not a hole today**, and the reasoning matters more than the verdict:

- The genuinely administrative routes use the STRONGER gate. `approve`, `decline` and
  `admin/backfill-projects` all check `isOwner(r.drive_email, env)`, which is the env allowlist and
  cannot be granted by any database row.
- Every remaining ungated route is **self-scoped**: it resolves the caller's own researcher row and
  acts on the caller's own Google Drive. A pending account calling `drive-purge`, `projects/create`
  or `drive-estate` reaches nothing but its own folders. Unpleasant for them, invisible to everyone
  else.
- The two things a pending account genuinely must not do — create an instance (which mints invites
  and consumes the estate) and write account settings — are among the four that ARE gated.

**⚠ What changes in Phase C.** "Self-scoped" stops being a synonym for "safe" the moment an endpoint
resolves a PROJECT rather than the caller, because the project's Drive belongs to its owner, not to
the caller. `drive-estate`, `drive-file`, `drive-purge`, `trash` and the `projects/*` routes are all
on that list. If approval is still not checked when they become project-scoped, an unapproved member
inherits reach into the owner's estate.

**Recommendation (do the first now, the second with Phase C):**
1. **Correct the comment today.** It overstates the guarantee, and an overstated comment is how the
   next reader skips adding the check.
2. **Make approval explicit on every mutating route as part of Phase C**, alongside `authMember`.
   Not before: adding `isApproved` to self-scoped routes today would lock pending researchers out of
   their own Drive for no benefit.

## F2 — Visibility filtering: the "paper on the front end" case, not yet load-bearing

Seth, locked: *"the access filter needs to not be paper on the front end."*

Today the panel hides things — the Unassigned card, the storage modal's rows, per-device actions —
and today that is honest, because `GET /v1/researcher` returns only the caller's own instances. There
is nothing hidden that the caller is not entitled to.

⚠ **Phase C is where a hidden-in-the-client filter would become a real leak.** II.4 already specifies
the fix (`GET /v1/researcher?project=<id>` returns the list FILTERED by the member's `see`, with
`has_key` reflecting their own grants). **Recommendation: build the server filter in the same commit
as the member UI, never after it.** A window in which the panel hides what the API returns is
precisely the thing Seth ruled out, and it is very easy to create accidentally by shipping the UI
first because it demos better.

## F3 — Correctly client-side and must STAY: the unassigned sweep predicate

The panel decides which docs are unassigned; the worker moves exactly the ids it is given.

**This cannot move server-side, by construction:** device inventories are E2EE, so the worker cannot
know what any device holds. It is recorded here so that a future reader sweeping for "client-side
guards" does not mistake it for an oversight and "fix" it into a worker that has to be able to read
inventories — which would mean abandoning the E2EE property to satisfy a tidiness rule.

Same category: anything that reasons over decrypted inventory. The dividing line is not
client-versus-server, it is **what the worker is structurally able to see**.

## F4 — Device-capability gates (`engNum`) are client-side and belong there

`canDelText = engNum >= 94`, `canSetDone = engNum >= 138`: these ask *"will the far end understand
this command?"*, not *"is the caller allowed?"*. Sending an unsupported command to an old device is
a no-op, not a privilege escalation. Correctly client-side.

⚠ Their real hazard is already documented elsewhere and is about drift, not authorization: `engNum`
parses `ENGINE_VERSION` after stripping non-digits, so a non-numeric version string silently
collapses to a small number and disables capabilities on perfectly capable devices. That is why
`ENGINE_VERSION` must stay `vNNN` and `BUILD_TAG` carries the name.

## F5 — Rate limiting shrank when the password lane was retired, and nobody noticed

`SIGNUP_LIMIT` used to cover signup, salt, login, reset-request, reset-verify and reset-confirm. Those
routes were deleted in v433, so today the limiter covers only **2FA attempts** and **crowd
submissions**.

Not urgent — what is left is either authenticated or Turnstile-gated — but two gaps are worth a
deliberate decision rather than being an accident of a deletion:

- **The Google OAuth start/callback has no limit.** It is the one unauthenticated route that does
  real work (a token exchange plus D1 writes).
- **`GET /v1/researcher/drive-estate` has no limit and is expensive**: two full `driveListAll` passes
  (paged to 20k files each) plus a D1 read, and the panel polls it. One researcher with several
  browser tabs open is the realistic load, not an attacker.

**Recommendation:** low priority, but add a limit to the OAuth callback when the worker is next
touched, and consider a short server-side cache on `drive-estate` — which would also reduce Drive
API pressure, the thing that actually rate-limits us.

## F6 — Already server-side, verified, no action

Recorded so the audit is a map rather than a list of complaints:

- **Folder-name sanitization** — `projects/create` and `driveEnsureDefaultProject` both strip
  `\ / : * ? " < > |`, trim, and cap at 120 chars. The client does not have to be trusted for it.
- **Upload size and quota** — `MAX_FILE_BYTES` / `MAX_TOTAL_BYTES` enforced in `worker/src/index.js`.
- **Move destinations** — a crowd recorder cannot be a move target because crowd recorders are a
  different TABLE; `/move` resolves an `instance` row and requires `toId !== instanceId`, with
  `/adopt` kept deliberately separate rather than as a relaxation. Structural, not policy.
- **The wrap-to-owner invariant** — `POST /v1/researcher/keys` rejects any grant set lacking the
  project owner's copy. Owner key sovereignty is enforced where it cannot be bypassed.
- **Turnstile, escrow, approval logging** — server-side throughout.
- **Drive folder dedupe** — id-first with `files.get` (strongly consistent), tag search as fallback.

## F7 — The drift detector: what this audit says about where it lives

Seth's original question was whether drift guards belong in the worker, and whether a scheduled
detector is workable on the free tier.

This audit's answer is **yes, and it should read the same derivation the app does rather than
re-implement the rules** — the design already recorded is invariants over `buildDriveEstate` rather
than hand-written checks, precisely so it cannot drift from what it is checking. Nothing found here
changes that. What this audit adds is a note on scope: the detector can only check what the worker
can SEE (F3), so it can verify folder structure, parentage, project membership and D1/Drive
agreement — and it can never verify anything about device inventories.

## Ranked recommendation

| # | Action | When |
|---|---|---|
| 1 | Correct the `isApproved()` comment so it stops promising a gate that is not there | now, one line |
| 2 | Server-side `see` filtering built in the SAME commit as any member UI | with Phase C, non-negotiable |
| 3 | Explicit approval checks on mutating routes as they become project-scoped | with Phase C |
| 4 | Rate-limit the OAuth callback; consider caching `drive-estate` | next worker touch |
| 5 | Drift detector over `buildDriveEstate` invariants | after Phase C |

⚠ **Every item on that table is a WORKER change, and worker changes get the maintenance flag**
(Seth, 2026-08-20: *"We probably need the maintenance flag at some point when we're ready to start
pushing worker changes and/or if we do any moving of client-side things to the worker. Those have a
high risk potential of breaking something."*). Moving a guard from the client to the worker is the
highest-risk shape of change this suite has: the guard changes meaning at the same moment its
enforcement point moves, so a mistake is not "the check is missing" but "the check now refuses
something it should allow" — which presents as the app being broken for everyone at once, with no
staged rollout, because the worker has exactly one live version. Raise the flag, deploy, confirm,
clear. The procedure is in CLAUDE.md.

⚠ **And prefer DUPLICATION over relocation while a guard is moving.** Adding the server check while
leaving the client check in place is additive, backward-compatible, and independently revertible; the
client check can be deleted a release later once the server one has been observed working. Removing
both halves in one deploy converts a recoverable mistake into an outage.

⚠ **The meta-finding.** The client is not where this codebase is weak. The weakness is that several
guards are safe today for a reason nobody wrote down — "it happens to be self-scoped" — and Phase C
removes that reason silently, without any of those routes changing shape enough to attract review.
This document exists so that when Phase C lands, the list of routes to re-check already exists.
